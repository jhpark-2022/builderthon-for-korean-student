# 배경 브리프: 세로 화면에서 파문이 너무 빨리 퍼집니다

대상 레포: `website` (커밋 `a1c16a4` 기준). 바꾸는 줄은 `lib/background/shaders/water.ts` 한 곳입니다.

감사 대상: https://naru-crossing-seoul.vercel.app/ (1440×900, 390×844, 스크롤 55% 고정, 0.7초 간격 8프레임, 프레임 간 잔차의 반경 프로파일로 파문 위치 추적).

## 0. 결론 한 줄

세로 패리티 작업(`9d56472`)에서 파문의 **감쇠**만 `K`로 줄이고 **파장과 진행 속도**는 그대로 두었습니다. 그래서 폰에서는 보이는 범위가 2.2배 좁아진 자리를 파문이 예전 속도로 지나갑니다. 화면 가로 대비 속도가 데스크톱의 2.3배입니다.

## 1. 실측

스크롤 55% 지점을 고정하고 0.7초 간격으로 여덟 장을 찍은 뒤, 프레임 평균을 뺀 잔차에서 파문 마루의 반경을 쟀습니다. 파문의 중심은 셰이더와 같은 자리(`mx = 0.5`, `my = 0.325 + (uScroll - 0.16) × 0.45`)로 잡았습니다.

**데스크톱 1440×900**

| 시각 | 마루 반경 | 화면 가로 대비 |
| --- | --- | --- |
| 0.0s | 50px | 3.4% |
| 1.4s | 95px | 6.6% |
| 2.8s | 194px | 13.4% |
| 4.2s | 311px | 21.6% |
| 4.9s | 374px | 25.9% |

4.9초 동안 한 바퀴가 끝나지 않습니다. 진행 속도 **66px/s**, 화면 가로 대비 **초당 4.6%**. 한 주기 약 9.5초.

**폰 390×844**

| 시각 | 마루 반경 | 화면 가로 대비 |
| --- | --- | --- |
| 0.0s | 190px | 48.7% |
| 0.7s | 122px | 31.4% (새 파문으로 넘어감) |
| 1.4s | 97px | 24.9% |
| 2.8s | 131px | 33.5% |
| 3.5s | 198px | 50.9% |
| 4.9s | 241px | 61.7% |

4.9초 안에 한 바퀴가 끝나고 다음 파문이 시작됩니다. 진행 속도 **41px/s**, 화면 가로 대비 **초당 10.5%**. 한 주기 약 4.2초.

절대 속도는 폰이 오히려 느립니다(41 대 66px/s). 그런데 **화면 가로 대비로는 2.3배 빠릅니다.** 사람은 절대 픽셀이 아니라 화면 대비로 봅니다.

## 2. 원인

`lib/background/shaders/water.ts`의 두 줄입니다.

```glsl
float phase = rr * 9.0 - uTime * (0.5 + uFlow * 1.6) - uScroll * 7.0;
float rings = smoothstep(0.86, 1.0, sin(phase)) * exp(-rr * 2.4 * K);
```

`rr`은 화면 **높이** 단위의 거리입니다(`q.x`에 `uAspect`를 곱하므로). 패리티 브리프에서 넣은 `K`는 좁은 화면에서 반지름 기준을 가로로 맞추는 계수이고, 지금은 `2.4`(감쇠)에만 붙어 있습니다.

그 결과 폰에서(K = 1/0.462 = 2.165):

| 값 | 데스크톱 | 폰 | 비고 |
| --- | --- | --- | --- |
| 보이는 범위(감쇠 0.1까지) | 0.96h = 864px = 가로 60% | 0.44h = 374px = 가로 96% | K가 줄였습니다 |
| 파장(`2π / 9`) | 0.70h = 628px | 0.70h = 589px | **K가 안 붙었습니다** |
| 보이는 범위 ÷ 파장 | 1.38개 | 0.63개 | 폰에서는 파문 한 개도 다 안 들어옵니다 |
| 진행 속도 | 4.6%/s | 10.5%/s | 2.3배 |

파문이 태어나서 사라질 때까지 지나야 하는 거리(보이는 범위)는 2.2배 줄었는데, 지나가는 속도(파장 × 주파수)는 그대로입니다. 그래서 수명이 절반 이하가 되고, 같은 시간에 두 배로 자주 반복됩니다.

`- uScroll * 7.0` 항도 같은 이유로 과합니다. 스크롤 한 단위당 파문이 0.778h를 나아가는데, 그게 폰에서는 보이는 범위의 1.76배이고 데스크톱에서는 0.81배입니다. **스크롤할 때 특히 빨라 보이는 이유가 이것입니다.**

## 3. 고치기

### 3.1 [P0] 파문의 공간 주파수에도 `K`를 곱합니다

한 글자만 바뀝니다.

```glsl
    // 2026-09-19 (파문 속도 브리프): rr * 9.0에 K를 곱합니다. 패리티 브리프에서
    // 감쇠(2.4)에만 K를 붙이는 바람에, 폰에서 보이는 범위는 2.2배 좁아졌는데
    // 파장과 진행 속도는 그대로였습니다. 파문이 좁아진 자리를 같은 속도로 지나가니
    // 수명이 절반이 되고 두 배로 자주 반복됐습니다(실측 가로 대비 10.5%/s 대 4.6%/s).
    //
    // 공간 주파수에 K를 곱하면 셋이 한꺼번에 맞습니다.
    //   진행 속도    dr/dt = w / (9K)            → 폰 41px/s가 19px/s로, 가로 대비 4.9%/s
    //   파장 대 범위  (2pi/9K) 대 (2.3/2.4K)      → K가 약분되어 두 화면 모두 1.38개
    //   스크롤 반응   dr/duScroll = 7 / (9K)      → 두 화면 모두 범위의 0.81배
    // 가로 화면은 K = 1.0이라 이 줄은 항등입니다. 데스크톱은 한 픽셀도 바뀌지 않습니다.
    float phase = rr * 9.0 * K - uTime * (0.5 + uFlow * 1.6) - uScroll * 7.0;
```

**이 한 줄이 전부입니다.** 감쇠의 `* K`는 그대로 둡니다. 다른 상수를 만지지 마세요.

### 3.2 [P1] 여기까지 하고 다시 보세요

아래 둘은 3.1을 배포하고 실제 폰에서 확인한 뒤에도 빠르게 느껴질 때만 합니다. **같은 커밋에 넣지 마세요.** 3.1만으로 충분할 가능성이 높고, 셋을 한 번에 바꾸면 무엇이 효과였는지 알 수 없습니다.

**(a) 손가락 속도 게인.** `uFlow`는 초당 문서의 60%를 지나는 속도를 1로 봅니다(`BackgroundScene`의 `perSec / 0.6`). 이 페이지에서 그건 폰 6,153px/s, 데스크톱 5,138px/s입니다. 폰의 관성 스크롤은 그 속도에 쉽게 닿지만 마우스 휠은 거의 닿지 않습니다. 그래서 같은 "빠르게 넘김"인데 폰은 `uFlow`가 1에 가깝고(파문 각속도 2.1rad/s) 데스크톱은 0.3 언저리입니다(0.98rad/s). 필요하면 세로에서만 게인을 낮춥니다.

```glsl
float phase = rr * 9.0 * K - uTime * (0.5 + uFlow * 1.6 * mix(1.0, 0.55, portrait)) - uScroll * 7.0;
```

**(b) 파문 중심의 이동.** `my`가 스크롤 동안 0.45h를 내려옵니다. 폰에서 380px인데 보이는 범위의 반지름이 374px이라, 중심 자체가 파문 크기만큼 지나갑니다(데스크톱은 405px 대 864px으로 절반). 다만 이 이동에는 이유가 있습니다. 멈춰 있으면 주황 점이 한 문단 뒤에 박힌 채로 그 문단을 읽게 됩니다. 완전히 보정하면(`/ K`) 폰에서 페이지 전체를 통틀어 176px만 움직여서 사실상 고정입니다. 그래서 절반만 보정합니다.

```glsl
float my = 0.325 + max(uScroll - 0.16, 0.0) * 0.45 / mix(1.0, sqrt(K), portrait);
```

## 4. 절대 하지 말 것

- `exp(-rr * 2.4 * K)`의 `K`를 빼거나 값을 바꾸지 마세요. 그건 패리티 브리프가 넣은 것이고 맞습니다.
- `rr * 9.0`의 `9.0`을 다른 숫자로 바꾸지 마세요. 그러면 데스크톱도 같이 바뀝니다. 바꾸는 것은 `* K`를 붙이는 것뿐입니다.
- `uTime` 계수 `0.5`를 낮추지 마세요. 그건 두 화면 공통이고, 데스크톱은 지금 속도가 맞습니다.
- `K`의 정의(`mix(1.0, clamp(1.0/max(uAspect,0.001), 1.0, 2.4), portrait)`)를 바꾸지 마세요. 등불 번짐과 나루 점 무리가 같은 `K`를 씁니다.
- 3.1과 3.2를 한 커밋에 넣지 마세요.
- DOM, 카피, `data/naru.ts`, 라우트, 수파베이스는 범위 밖입니다.

## 5. 검증

1장과 같은 방법으로 다시 재세요. 재현 절차입니다.

1. 두 프로파일(1440×900, 390×844)로 페이지를 열고 배경이 뜰 때까지 기다립니다(`window.__naruBackgroundStarted`).
2. `scrollTo(0, 0.55 * (docH - vh))`로 고정하고 4초 기다립니다.
3. 0.7초 간격으로 여덟 장을 찍습니다. **스크롤을 움직이지 마세요.** DOM은 보이는 채로 둡니다(고정 스크롤이라 다음 단계에서 상쇄됩니다).
4. 여덟 장의 휘도 평균을 뺀 잔차에서, 중심 `(0.5W, (1 - my)H)`, `my = 0.325 + (0.55 - 0.16) × 0.45` 기준 반경 프로파일을 만들고 마루의 반경을 추적합니다.

| # | 항목 | 기준 |
| --- | --- | --- |
| 1 | 폰 파문의 가로 대비 진행 속도 | **초당 6% 이하** (지금 10.5%, 데스크톱 4.6%) |
| 2 | 폰 파문의 한 주기 | **8초 이상** (지금 4.2초, 데스크톱 약 9.5초) |
| 3 | 데스크톱 여덟 프레임 | 적용 전과 **픽셀 차이 없음**. `K = 1.0`이므로 당연히 그래야 합니다 |
| 4 | 폰에서 파문이 여전히 보이는가 | 육안으로 확인. 느려지는 것이지 사라지는 것이 아닙니다 |
| 5 | 폰 파문의 가로 지름 | 뷰포트 가로의 45% 이하(패리티 브리프 검증 6과 같음) |
| 6 | 본문 대비 | 폰 `#december`·`#gains`·`#join`의 흰 글자가 4.5:1 이상 |
| 7 | 모션 민감 | `prefers-reduced-motion: reduce`에서 변화 없음 |

**3번이 이 작업의 안전선입니다.** 가로 화면에서 `K`는 1.0이고 `rr * 9.0 * 1.0`은 `rr * 9.0`입니다. 데스크톱이 조금이라도 달라졌다면 `K`의 정의를 건드린 것입니다.
