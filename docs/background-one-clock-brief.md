# 배경 브리프: 시계가 둘입니다

대상 레포: `website` (커밋 `9629d96` 기준). 바꾸는 파일은 `lib/background/` 안뿐입니다. DOM, 카피, 라우트, 수파베이스, `/2026-08`은 건드리지 않습니다.

계측 대상: https://naru-crossing-seoul.vercel.app/ (1440×900 문서 10,499px, 390×844 문서 12,871px). 스크롤 0~98%를 13지점으로 나눠 캔버스를 찍고 픽셀 통계를 냈습니다.

## 0. 결론 한 줄

배경에 있는 것들은 각자 잘 만들어져 있는데, **둘로 나뉜 시계를 보고 움직입니다.** 하나는 문서 전체에 대한 비율(`uScroll`)이고 하나는 챕터의 DOM 위치(앵커)입니다. 이 둘이 서로를 모르기 때문에 사건들이 어긋나고, 카피를 한 줄 더할 때마다 더 어긋납니다.

### 2.2 문제 넷

**첫째, 주황이 한 번 완전히 꺼집니다.** 스크롤 22% 지점에서 주황 픽셀이 **0.02%**입니다. 해는 17%까지 꺼졌고 나루 점은 9%까지밖에 안 떠올랐습니다. 두 불빛의 교대가 **둘 다 거의 보이지 않는 지점에서** 일어납니다.

이게 가장 아픈 곳입니다. `shaders/water.ts`의 주석이 스스로 이렇게 적어 놓았습니다. "링과 점이 로고입니다. (…) 배경과 로고가 같은 것을 말하게 하는 유일한 연결선이에요." 그 연결선이 800px 동안 끊깁니다. 그리고 다시 켜지는 주황은 **꺼진 그 불이 아니라 다른 불로 보입니다.** 해가 지고, 한참 뒤에, 다른 자리에서 다른 점이 뜹니다.

**둘째, 수면과 서울이 1,800px 동안 겹칩니다.** 서울 윤곽이 다 떠오른 y 1,820에서 수면은 아직 37% 살아 있습니다. 밤바다 위에 서울 지도가 떠 있는 화면이 한참 이어집니다. 하나가 끝나고 하나가 시작하는 것이 아니라 두 장면이 포개져 있습니다.

**셋째, 파문 링이 아무것과도 관계가 없습니다.** `uRingPhase`(시간)와 `uScroll × 7`로 굴러가는 연속 파형이라, 형상이 바뀌든 점이 뜨든 상관없이 같은 속도로 계속 퍼집니다. 40%와 80% 지점에서 링이 가장 크고 밝은데, 그 자리에는 링이 커질 이유가 없습니다. 그래서 배경에서 가장 눈에 띄는 움직임이 가장 뜻이 없는 움직임입니다.

**넷째, 카피를 고치면 어긋남이 커집니다.** 이 세션에서 문서가 9,493px에서 10,499px로 11% 늘었습니다. 앵커로 묶인 셋은 챕터를 따라갔고, `uScroll`로 묶인 다섯은 전부 11%씩 뒤로 밀렸습니다. **아무도 배경을 건드리지 않았는데 배경의 순서가 바뀌었습니다.** 앞으로도 그렇습니다.

### 2.3 문제가 아닌 것

확인해 보고 뺀 것들입니다.

- 형상은 잘리지 않습니다. 화면 가로 대비 서울이 데스크톱 52% · 폰 72%, 싱가포르가 데스크톱 67% · 폰 85%로 양쪽 다 화면 안에 있습니다.
- 두 화면의 형상 크기 차이(52% 대 72%)는 의도된 것입니다(`config.ts`의 주석). 그대로 둡니다.
- 점 개수, 점 크기, 밝기는 9월 19일에 맞춘 값이고 지금 화면에서 잘 읽힙니다. 건드리지 않습니다.

## 3. 제안: 하나의 시계, 하나의 불빛

### 3.1 시계를 하나로

`uScroll`이 아니라 **챕터 앵커에서 계산한 진행도**로 배경의 사건을 움직입니다. 앵커는 이미 읽고 있는 `#top` 하단과 `#naru`에 `#gains`만 더하면 됩니다.

네 구간으로 나눕니다.

| 구간 | 언제부터 언제까지 | 무슨 일이 |
| --- | --- | --- |
| 0 · 나루터 | 페이지 시작 ~ `#top` 하단 | 수면, 지평선, 해. 형상 없음 |
| 1 · 건넘 | `#top` 하단 ~ `#gains` 상단 | **해가 물 속으로 내려가 나루 점이 됩니다.** 수면이 가라앉습니다 |
| 2 · 서울 | `#gains` 상단 ~ `#naru` − 0.5화면 | 서울 윤곽이 나루 점 둘레에 섭니다 |
| 3 · 크로싱 | `#naru` − 0.5화면 ~ + 1.0화면 | 서울이 싱가포르로 건넙니다 |
| 4 · 잦아듦 | 그 뒤 | 형상이 어두워집니다 |

`BackgroundScene`에서 구간 진행도 `s1`, `s2`를 계산해 `WaterSurface`에 새 유니폼 `uStage1`, `uStage2`로 넘깁니다. 셰이더에서 `uScroll`을 쓰던 자리를 이 값으로 바꿉니다. `uScroll`은 물살(`cur`)의 흐름에만 남깁니다. 그건 페이지가 얼마나 흘렀는지를 말하는 것이 맞습니다.

### 3.2 불빛을 하나로

**이 브리프의 핵심입니다.** 해와 나루 점을 교대가 아니라 **같은 불빛의 이동**으로 만듭니다.

둘은 이미 같은 자리에서 시작합니다. 해는 화면 `(lx, H)`에 있고 `H`는 0.315에서 내려가며, 나루 점은 `(lx, 0.325)`에서 시작합니다. `water.ts`의 주석이 그렇게 적어 놓았어요. **자리는 맞는데 시간이 안 맞습니다.**

구간 1에서 둘을 상보로 묶습니다.

```glsl
// 구간 1: 해가 수면 아래로 내려가 나루 점이 됩니다. 한 불빛입니다.
// 전에는 해가 smoothstep(0.02,0.30,uScroll)로 꺼지고 점이 smoothstep(0.16,0.48,uScroll)로
// 떠서, 스크롤 22% 지점에 둘 다 거의 꺼진 구간이 800px 생겼습니다(주황 픽셀 0.02%).
// 이제 합이 항상 1입니다. 어느 순간에도 주황은 정확히 하나 있습니다.
float sunAlive = 1.0 - uStage1;
float dotAlive = uStage1;
```

그리고 `H`(지평선)를 구간 1 동안 계속 내려서 **불빛이 수면을 뚫고 들어가는 것이 보이게** 합니다. 지금은 제자리에서 흐려집니다. 내려가야 "건넜다"로 읽힙니다.

교차점(`uStage1 = 0.5`)에서 해의 화면 좌표와 점의 화면 좌표가 **같아야 합니다.** 지금 `H`는 `0.315 - uScroll*0.045`에서 시작하고 점은 0.325에서 시작하므로 1% 차이입니다. 교차점에서 둘을 같은 값으로 맞추세요(검증 4번).

### 3.3 파문을 사건에 묶습니다

지금 `phase`의 `- uScroll * 7.0` 항을 뺍니다. 그 자리에 **사건 진폭**을 둡니다.

```glsl
// 파문은 두 번 크게 입니다. 불빛이 물에 들어갈 때(구간 1 한가운데)와
// 형상이 건널 때(구간 3 한가운데). 그 밖에는 잔물결만 있습니다.
// 전에는 uScroll × 7 로 계속 같은 속도로 퍼져서, 배경에서 가장 눈에 띄는
// 움직임이 가장 뜻이 없는 움직임이었습니다.
float bell(float x){ float d = abs(x - 0.5) * 2.0; return 1.0 - smoothstep(0.0, 1.0, d); }
float ringGain = 0.28 + 0.72 * max(bell(uStage1), bell(uMorph));
```

`rings`에 `ringGain`을 곱합니다. `uMorph`는 `ParticleField`가 이미 받는 값이라 `WaterSurface`에도 같은 값을 넘기면 됩니다.

### 3.4 넘겨주기를 깨끗하게

서울 윤곽의 등장을 **구간 1이 끝난 뒤**로 옮깁니다. 지금은 `#top` 하단부터 떠올라서 수면이 60% 남아 있을 때 이미 지도가 보입니다.

```
구간 0  수면 + 해
구간 1  해가 내려가 나루 점이 됨. 수면이 가라앉음. 형상 없음
구간 2  나루 점 둘레에 서울이 섬
구간 3  서울이 싱가포르로 건넘
구간 4  잦아듦
```

이러면 화면에 한 번에 한 장면만 있고, 매 순간 주황 불빛이 정확히 하나 있고, 파문은 그 불빛에 무슨 일이 일어날 때만 큽니다.

## 4. 절대 하지 말 것

- **점 개수·점 크기·형상 폭·밝기를 바꾸지 마세요.** 9월 19일에 양쪽 화면에서 맞춘 값입니다(`config.ts`의 `points`, `edgePx`, `edgePxLandscape`, `landscapeW`, `portraitW`, `singaporeW`).
- **파문의 공간 주파수 `rr * 9.0 * K`와 감쇠 `2.4 * K`를 바꾸지 마세요.** 9월 19일 두 브리프가 맞춘 값입니다. 바꾸는 것은 진폭(`ringGain`)뿐입니다.
- **`uRingPhase` 적분을 되돌리지 마세요.** 곱셈으로 돌아가면 위상이 점프합니다(`docs/background-ring-jump-and-singapore-detail-brief.md`).
- **`K` 보정의 정의를 바꾸지 마세요.** 좁은 화면의 반지름 기준입니다.
- **시간(`uTime`)으로 사건을 움직이지 마세요.** 배경의 사건은 전부 스크롤이 만듭니다. 그래야 모션 민감 설정과의 관계가 지금과 같습니다(저절로 시작하는 움직임이 아니므로 WCAG 2.2.2의 대상이 아님). 잔물결과 물비늘만 시간을 씁니다.
- **`crossing`과 `field` 변형을 건드리지 마세요.** `/2026-08`이 `field`를 씁니다. 출력이 바이트 단위로 같아야 합니다.
- **앵커를 못 읽었을 때의 대비를 지우지 마세요.** `#gains`가 없으면 `#record`, 그것도 없으면 지금의 `fallbackAnchors`로 떨어집니다.
- em dash 금지. 결정은 `DECIDED 2026-09-23` 한국어 주석으로.

## 5. 검증

캔버스만 보려면 DOM을 지우지 말고 `header,main,footer`의 `opacity`를 0.06으로 낮추세요. 지우면 배경이 함께 사라집니다(`Background.tsx`의 폴백).

| # | 항목 | 기준 |
| --- | --- | --- |
| 1 | 주황이 끊기지 않음 | 스크롤 0~60%를 20지점으로 나눠 주황 픽셀 비율을 잴 때, **모든 지점에서 0.35% 이상** (지금 22% 지점에서 0.02%) |
| 2 | 가장 어두운 지점 | 같은 20지점의 평균 휘도 최솟값이 **12.5 이상** (지금 11.15) |
| 3 | 겹치지 않음 | 수면의 알파가 0.15를 넘는 지점과 형상의 알파가 0.15를 넘는 지점이 **겹치지 않음** |
| 4 | 불빛이 이어짐 | `uStage1 = 0.5`에서 해의 화면 y와 나루 점의 화면 y 차이가 **화면 높이의 1% 이내** |
| 5 | 파문의 뜻 | 링 진폭의 최댓값이 구간 1과 구간 3의 한가운데에 있고, 구간 2 한가운데에서는 최댓값의 **40% 이하** |
| 6 | 시계가 하나 | 셰이더에서 `uScroll`을 읽는 곳이 물살(`cur`) 하나뿐 |
| 7 | 문서 높이 독립 | 카피를 더해 문서를 10% 늘렸을 때, 각 사건이 일어나는 **챕터가 같음**(y는 달라도 됨) |
| 8 | 두 화면 | 1~5번을 1440×900과 390×844에서 각각 |
| 9 | 모션 민감 | `prefers-reduced-motion: reduce`에서 스크롤로 만든 변화는 그대로, 시간으로 만든 잔물결은 멈춤 |
| 10 | 아카이브 | `/2026-08` 배경이 적용 전과 픽셀 차이 없음 |
| 11 | 프레임 | 폰 프로파일에서 초당 프레임이 적용 전보다 15% 넘게 떨어지지 않음 |
| 12 | em dash | 0건 |

**7번이 이 작업의 진짜 목표입니다.** 지금은 카피 한 줄이 배경의 순서를 바꿉니다.
